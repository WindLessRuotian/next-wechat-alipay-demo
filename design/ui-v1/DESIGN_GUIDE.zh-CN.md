# PayBridge UI 设计交付说明

版本：V1.0  
日期：2026-10-25  
适用项目：Next.js 微信与支付宝登录、支付集成演示

## 1. 交付内容

本方案是独立的高保真 UI 设计，不是已接入业务接口的新前端。

| 文件 | 用途 |
| --- | --- |
| [index.html](index.html) | 自包含可交互预览，可直接在浏览器打开；无需安装依赖 |
| [设计总览长图](screens/00-design-overview.png) | 一次查看核心业务、辅助页面、状态和移动端方向 |
| [PayBridge-UI-Design.pdf](PayBridge-UI-Design.pdf) | 适合评审的多页设计图册，文字已栅格化 |
| [screens](screens/) | 各页面独立 PNG，包括桌面、移动端、失败及关闭状态 |
| 本文档 | 视觉规范、页面映射、业务边界与落地建议 |

预览工具栏支持「设计总览」「产品预览」「组件与状态」「移动端」切换。
右上角下拉框可直接进入指定页面。

可操作路径：

1. 登录 → Mock 授权 → 控制台。
2. 控制台 → 购买 → 微信待支付 → 模拟成功或失败。
3. 购买 → 选择支付宝 → 跳转说明 → Mock 收银台 → 结果。
4. 订单列表 → 状态筛选、渠道筛选、搜索、分页、详情。
5. 订单详情 → 取消确认 → 关闭结果。
6. 组件与状态 → 网络异常、授权失效、账号冲突等提示。

所有身份和订单都是固定设计示例。原型交互只改变页面内的展示状态，刷新后可以重置，不代表服务端数据更新。二维码为不可支付的设计示意，不能用于真实扫码授权或付款。

## 2. 设计方向

采用常见企业级 SaaS / B 端工作台样式，以熟悉的布局和业务可读性为核心，而不是追求营销页的大面积装饰。

- 浅灰背景、白色内容卡片、蓝色主按钮。
- 左侧稳定导航、顶部位置提示、独立环境说明条。
- 页面标题、摘要、主任务、辅助信息四层结构。
- 中性灰展示内容，语义色表达状态，不让每个模块都争夺注意力。
- 微信绿、支付宝蓝只用于渠道识别，不替代应用品牌色。
- 金额和订单编号采用稳定的数字与等宽文字样式。
- 重要操作提供明确动词；取消、退出等操作带确认反馈。
- 不添加未实现的商户管理、退款、财务结算或营销模块。

设计名暂定 **PayBridge**，属于展示品牌，可以在后续实现时替换为公司的正式产品名。

## 3. 页面与现有路由

| 设计页面 | 当前业务对应位置 | 核心内容 |
| --- | --- | --- |
| 登录 | `/` | 微信、支付宝登录入口；首次授权说明；Mock 标识 |
| 控制台 | `/dashboard` | 用户信息、账号关联、购买入口、近期订单 |
| 确认订单 | `/checkout` | 服务端价格展示、渠道选择、金额摘要 |
| 微信待支付 | `/orders/[id]` | 二维码、倒计时、待支付状态、订单详情 |
| 我的订单 | `/orders` | 当前用户订单、状态、金额、时间、详情入口 |
| 支付结果 | `/orders/[id]` | paid / failed / closed 的独立视觉状态 |
| Mock 授权 | `/mock/oauth/[provider]` | 示例身份、授权允许与取消 |
| Mock 收银台 | `/mock/alipay/gateway` | 模拟金额、交易信息、成功与关闭操作 |
| 支付宝跳转说明 | 下单后的前端过渡态 | 说明即将前往收银台，返回后查询服务端 |
| 组件与状态 | 设计交付页面，不新增业务路由 | 正常、异常、加载、空状态、确认弹窗 |

新增视觉层的统计卡片、订单筛选和分页属于设计建议，不意味着当前应用已有相同界面或分页接口。
统计数据应由当前用户自己的订单计算，不能读取其他用户或展示全平台交易。

### 登录与注册

- 不设计单独的密码注册页面。首次官方授权成功后，由服务端创建本地用户。
- 应用只提供入口与回调结果；官方微信扫码页面、支付宝授权页由平台提供。
- 不仿制官方登录页面，也不通过设计中的二维码收集真实身份。
- 关联账号必须保留归属校验，不能因为界面显示“已关联”而跳过服务端检查。

### 结账与付款

- 商品金额固定来自服务端，客户端没有金额输入框。
- 微信 Native 下单后在订单详情显示二维码，延续现有路由结构。
- PDF 要求的 checkout 二维码位置与现有详情页之间仍有差异；本稿不暗示该差异已修复。
- 支付宝下单后进入收银台；浏览器返回不能直接宣布成功。
- Mock 工具与用户付款操作分区；真实和沙箱模式应隐藏这些工具。
- 手动重放通知只属于演示能力，不应在生产用户界面出现。
- 倒计时归零不能在浏览器自行认定订单已关闭，必须等待服务端结果。

## 4. 视觉规范

### 颜色

| 角色 | 值 | 使用场景 |
| --- | --- | --- |
| 主色 | `#2563EB` | 主按钮、导航选中、重要链接 |
| 主色强调 | `#1D4ED8` | 主按钮悬停 |
| 页面背景 | `#F5F7FA` | 工作台背景 |
| 卡片 | `#FFFFFF` | 内容容器 |
| 主要文字 | `#182230` | 标题、关键数值 |
| 正文 | `#475467` | 说明、表格内容 |
| 次要文字 | `#667085` | 辅助信息 |
| 边框 | `#E7EBF1` | 卡片、分隔线 |
| 成功 | `#067647` / `#ECFDF3` | 已支付、已关联 |
| 警告 | `#934B0B` / `#FFFAEB` | 待支付、模拟环境、倒计时 |
| 错误 | `#B42318` / `#FFF1F0` | 支付失败、授权异常 |
| 微信识别 | `#16A260` | 微信渠道图标 |
| 支付宝识别 | `#1677FF` | 支付宝渠道图标 |

渠道矢量图标用于识别性示意，正式交付应核对平台的品牌标识使用规范。

### 字体与尺寸

- 字体：系统无衬线字体优先；Windows 使用 Segoe UI / Microsoft YaHei。
- 页面标题 26px，卡片标题 17px，正文 14px，辅助信息 12px。
- 数值 28–38px，状态标签 12px，订单编号使用等宽字体。
- 画板标注、小型说明等设计辅助文字允许更小，不应直接作为正式产品全部正文的尺寸。
- 卡片圆角 12px，控件圆角 6–8px。
- 以 8px 为主要间距单位，配合 12px、20px 等紧凑排版间距。
- 桌面主内容边距 30px，侧栏约 216px。
- 桌面参考画板 1440 × 1040，PNG 以 2 倍分辨率导出。
- 移动端参考视口 390 × 844，单屏 PNG 以 2 倍分辨率导出。

### 无障碍与交互

- 状态同时使用文字、图标或标记与颜色，不只依赖颜色。
- 主操作有清楚的键盘焦点样式。
- 输入框和图标按钮提供可访问名称。
- 弹窗使用原生 `dialog`，支持 Esc 关闭。
- 移动端主要操作高度不小于 44px；底部导航保留安全间距。
- 不使用强制动画；尊重降低动效偏好。
- 尚未进行完整 WCAG 审计，不能将本设计等同于无障碍认证。

## 5. 环境与状态

### 环境标识

| 环境 | 应展示的信息 | 不应出现 |
| --- | --- | --- |
| Mock | 淡黄色环境条，明确“不真实扣款”，分渠道标识 | “已完成真实平台联调”等误导描述 |
| Sandbox | 明确沙箱环境，提示使用沙箱账号 | Mock 成功、失败、通知重放按钮 |
| Live | 简洁正式环境标识，真实付款金额提示 | 模拟入口、测试身份、沙箱买家提示 |
| 混合模式 | 按微信和支付宝分别标识，不仅写一个全局模式 | 把一个渠道的真实能力扩大到另一个渠道 |

本轮画板统一使用 Mock 示例，以免在缺少企业凭据和实际联调结果时暗示真实能力已经可用。
Sandbox / Live 的业务切换仍由现有配置和服务端控制，设计原型不提供绕过配置的切换按钮。

### 九类关键状态

| 状态 | 用户看到什么 | 合理的下一步 |
| --- | --- | --- |
| 待支付 | 金额、有效期、渠道付款入口、同步提示 | 支付或取消 |
| 已支付 | 明确成功、确认时间、交易信息 | 查看订单或继续体验 |
| 支付失败 | 明确未完成付款，保留订单信息 | 重新购买 |
| 关闭 / 过期 | 二维码失效，不再显示支付按钮 | 创建新订单 |
| 加载 / 网络异常 | 保持已知状态，不直接判定支付失败 | 恢复连接并查询 |
| 空列表 / 无结果 | 区分无订单与筛选无结果 | 购买或清空筛选 |
| 授权失效 / 取消 | 清楚说明未建立会话 | 从登录入口重新授权 |
| 取消确认 | 说明关闭后不能继续付款 | 保留订单或确认关闭 |
| 关联冲突 | 提示已有账号归属，不覆盖关系 | 使用其他身份 |

还需在实际开发中连接：下单中的禁用状态、真实错误文案、轮询退避、请求取消、服务端字段缺失以及会话过期后的返回地址。

## 6. 移动端规则

- 侧栏改为控制台、购买、订单三项底部导航。
- 统计卡片改为两列；正文和支付区使用单列。
- 订单表格转为卡片，保留编号、状态、渠道、金额、时间和详情入口。
- 结账聚焦商品、渠道、最终金额，金额与主按钮靠近底部，内容区域预留避让空间。
- 正式产品的刘海屏安全区域需结合 `env(safe-area-inset-bottom)` 进一步校验。
- 手机上的微信 Native 二维码需要另一台设备扫码，不能误称为微信内 JSAPI 支付。
- 支付宝移动端应使用项目已有的移动网站支付能力。
- 单屏导出图只展示首屏；更多内容在可交互 HTML 中滚动查看。

## 7. 开发映射与建议顺序

1. 建立全局色彩、字体、圆角、间距变量和基础 Button / Badge / Card。
2. 改造应用布局、导航、环境提示、用户菜单。
3. 改造首页和账号展示，保留现有 OAuth 与服务端会话逻辑。
4. 改造 checkout 的渠道选择和订单摘要，不改变服务端金额来源。
5. 改造订单列表与详情，复用现有查询、轮询和关闭入口。
6. 将 Mock 工具放入独立区域，按渠道模式严格隐藏或显示。
7. 接入加载、异常、空状态、确认弹窗和移动端布局。
8. 使用已有测试加浏览器全流程回归，不只验证截图。

建议拆分的组件：

`AppShell`、`Sidebar`、`EnvironmentBanner`、`PageHeader`、`StatCard`、`ProviderBadge`、`PaymentMethodCard`、`OrderSummary`、`OrderStatusBadge`、`OrderTimeline`、`PaymentResult`、`MockToolsPanel`、`ConfirmDialog`、`EmptyState`。

本次没有修改 Next.js 页面、支付代码、数据库或环境配置，也没有自动提交或推送新设计文件。

## 8. 本轮验证范围

- 使用本地浏览器实际渲染桌面与移动视口并导出设计图。
- 验证原型登录、渠道选择、Mock 收银台跳转、结果页、订单筛选、分页、空结果、取消确认、网络提示和退出交互。
- 检查浏览器脚本异常，以及是否发出项目业务接口或外部平台请求。
- 设计预览不依赖外部字体、图片 CDN 或前端框架，不加载真实用户数据。
- 本轮不是业务功能验收，没有重跑原项目的支付测试，也没有进行真实微信或支付宝联调。
